# Design system: the sticker book

Kata (型, "form, pattern") is a daily journal with a companion that checks in on you, keeps a map of what you're working on, and people you share the good bits with. The look is a sticker book: warm paper, ink outlines, hard offset shadows, eight saturated hues, chunky condensed type. It replaced the quiet paper-and-seal look (rejected as too plain for everyone, 2026-10-29); don't drift back to it. Stay inside this system; change it here first if it has to change. Visual reference: `components/looks/HomeMock.tsx` (Sticker book) at `/looks`.

## Colour

- Tokens are CSS variables in `app/globals.css`: `--ground` (paper), `--surface` (a card), `--raised` (a recess inside a card), `--ink`, `--edge` (outlines and hard shadows: ink in the light theme, chalk in the dark), `--accent` (vermilion: Kata's seal and the one primary action per view), `--sun` (marker yellow: pressed, selected, the active tab, the writer's own bubble), `--ok` / `--bad` / `--warn` / `--info` (thread statuses), with `--on-accent`, `--on-sun`, `--on-hue`. Utilities: `bg-surface`, `text-ink/70`, `border-edge`, `bg-sun`…
- Eight hues (0 tomato, 1 sun, 2 sky, 3 mint, 4 grape, 5 pink, 6 teal, 7 orange). Put `data-hue={n}` on an element; inside it `bg-hue` is the saturated fill (text `text-on-hue`), `bg-tint` the soft tint and `text-deep` the readable text on that tint. Every thread and every person owns a hue (`thread.hue`, `user.hue`, `hueOf()` in `lib/social/dto.ts`). Colour says who or what; it is never decoration.
- Dark mode is designed, not inverted: chalk outlines on warm charcoal, tints go deep and deep text goes light. It follows the system unless `data-theme` is set on `<html>` (boot script in `app/layout.tsx`; `ThemeToggle` writes it). `.chapter` is the dark book in either theme.
- Contrast: small text is never lighter than `text-ink/65`. On a hue fill use `text-on-hue`; on a tint use `text-deep`.

## Type

- `font-display` is Bricolage Grotesque; `.font-display` makes it 800 weight at 84% width. Headlines, names, numbers, big labels. It has no italic: never write `italic` with it. Emphasise a word with `.mark` (a marker swipe) or `text-accent`.
- `font-sans` is Instrument Sans for everything else: interface, your writing, Kata's messages, letters. There is no serif.
- Sizes: `text-display-xl/-l/-m/-s`, `text-prompt`, `text-prose`, `text-lede`; UI at 1rem / 0.9375rem / 0.875rem, 0.8125rem minimum. Sentence case. No uppercase eyebrows, no mono labels.
- Fit-to-width headlines use container units (`[font-size:calc(100cqi/K)]` inside an `@container`).

## Shape and material

- `.card` is a sticker: surface, 2px `--edge` outline, `rounded-lg` (24px), a 5px hard shadow. Most content sits on cards. Inside a card use `.well` (a raised recess, no outline); never nest a card in a card.
- `.chip` is the pressable pill (outline, 3px shadow; `aria-pressed`, `aria-checked`, `aria-selected` or `aria-current` turns it sun), `.chip-sm` the small one. `.tag` is a small hue label (`data-hue`). `.scale` + `.scale-step` is one row of equal steps (the mood check, reactions, view switches); add `.scale-row` for side-by-side content. `.bubble-kata` (ink) and `.bubble-you` (sun) are the conversation. `.tape` is washi tape on a card (`data-hue`). `.control` is every input, `.writing` the borderless writing field, `.ruled` lined paper, `.link` an inline link, `.rule` a hairline colour inside cards (`border-t-2` for structure). `.press` gives buttons the sticker press; its shadow lives in the class so hover and active can move it, so never add a `shadow-*` utility to a `.press` element.
- Buttons: `Button` / `buttonClass` — primary (accent, one per view), secondary (surface), quiet, danger. All pills.
- Radii: `rounded-xs` 8px, `-sm` 12px, `-md` 16px (inputs, wells), `-lg` 24px (cards), `-xl` 32px, `rounded-full` (pills, avatars). Shadows are hard offsets (`shadow-sticker`, `shadow-sticker-sm`) on outlined things only; `shadow-float` only on floating UI.
- Tilt (±1–7°) only for things that are stuck on: map stickers, question cards, tape. Never on text people read at length.

## Motion

- One curve: `ease-out` = `cubic-bezier(0.22, 1, 0.36, 1)` (`EASE_OUT` in `lib/motion.ts`). UI 0.3–0.6s. Stickers press: hover lifts 1px onto a 4px shadow, active pushes 2px into a 1px one. `.appear` for new messages; `.typing` only while Kata is composing. No idle loops, no bounce. Reduced motion turns everything off.
- Landing motion is GSAP, imported lazily by one director (`components/landing/Scenes.tsx`) and wired to server markup by `data-*` hooks. `gsap.matchMedia` conditions cover every width (`desktop` / `compact`) and `reduce` opts out. The `staged:` variant applies only with JS (`html.js`) and no reduced-motion preference; runways and hidden before-states live behind it. GSAP absorbs CSS `translate`/`rotate`: on anything GSAP moves, let GSAP own centring and rotation.
- Inside the app, Framer Motion is fine for small transitions. The page wrapper in `AppShell` fades opacity only: a transform there would trap fixed bars.

## Maru, the seal and people

- The companion inside Kata is Maru by default, and each writer can rename it and choose what it calls them (`User.companionName` / `User.nickname`, empty means the default). Client components read both with `useCompanion()` (set by `AppShell`); server pages use `await namesFor(userId)`; landing and sign-in pages say Maru. A rename (Settings, onboarding's first step, or asking in chat) leaves a `names` receipt in today's conversation and the model's history starts after it, or the old name in it wins. Never hard-code "Maru" on a signed-in screen.
- Each writer also picks the colour it wears (`User.companionHue`: a hue 1–7, null for vermilion; `COMPANION_COLOURS` in `lib/companion/name.ts`). `AppShell` sets `data-maru` on the shell and on `<html>`, and `MaruMark` fills from `--maru`, so every face follows; `MaruColours` is the picker (Settings, onboarding's first step), and `set_names` takes a colour in chat.
- It speaks in `.bubble-kata` beside its face (`MaruMark`). `Seal` / `KataMark` (vermilion with 型 cut out) is Kata's own mark: the logo, a saved page, the 404. A person is an `Avatar`. Keep the three distinct.
- Work, not talk. Its messages carry receipts (`done`: what a tool did, each opening what it touched) and choices (`choices`: what it could do next), drawn by `Receipts` and `Choices` in `components/home/Work.tsx`. A tapped choice (`do:<i>`, or `do:no` for Not now) runs its stored tool in `runChoice` without the model. Text is one short line or nothing; a line that only restates a receipt is dropped. Anything that changed refreshes the page it's on (a `refresh` action), so client components that keep their props in state (`ThreadsBoard`, `Memories`) take new props when they arrive.
- It never asks an open question. A choice can carry a form (`inputs`: text with ideas to tap, number with a unit, date, pick, or a short list): when a tool is called without something it needs (no title, nothing to log), `askWithForm` offers the form instead of failing, and `offer_choices` with an argument left out gets one too (`formFor` in `tools.ts`). Complete choices are one tap, with a pen to change them first. `applyInputs` (`lib/companion/forms.ts`) checks what was filled in against the form; a choice that can't run stays open and the writer hears why. Check-ins on a thread that keeps numbers carry a log form, so logging never needs the model.
- Threads (`lib/db/models/Thread.ts`) are its mental model of you. They are private; only threads marked `shared` appear on a profile. Pages are always private; a moment or a reply is the only thing others see, and only ever as a choice the writer taps: `share_moment` and `draft_replies` make editable drafts, posted by `post_moment` / `post_reply`, which no model can call. A new name or bio is the same: `update_profile` drafts it and `save_profile` saves it on the tap. Orders about private things (a thread, a check-in time, the theme) just happen. A draft with a blank like `[book]` can't be posted until it's filled. A posted reply shows under its post at once (`replied` action, `REPLIED_EVENT`).
- A thread keeps up to four fields of its own (`Thread.fields`: a number with a unit and an optional daily goal, or words), made up for it: the model passes `track` to `create_thread` / `update_thread`, and `guessFields` (`lib/companion/fields.ts`, client-safe) suggests them from the title when it doesn't (a walk: minutes and km). Numbers keep one value per day (`days`, the last 60). `log_thread` sets a day's values (`add` for "another 15 min"), adds a field it's told about if there's room, and counts a habit as done. The Threads page logs, charts the last two weeks and edits fields (`ThreadFields`); logged numbers stay out of the thread's log.
- It's on every app page: `AskMaru` (in `AppShell`) opens today's conversation in a panel, by its button or ⌘K / Ctrl+K; home has the conversation on the page. The panel sends the path as `where` (it never offers to open the page you're on), and on phones it steps aside when it opens a page. Moments carry `data-screen-post`; every message sends the ids of the posts mostly in view and the one you're on (`components/shared/screen.ts`: last under the pointer, else the most visible), and the server reads them itself (`screenOf`, only what the writer may see) but gives them to the model only when the turn is about them (`aboutScreen`: pointing words, an author's name, "he" or "she" when asked from a post, or any of the last four messages being about one). A tapped answer (`say:`) carries the screen like typed words. Wanting to answer a post drafts replies at once; a question about a post ("what do you think?") gets Maru's take in words with no tools (`tool_choice: "none"`), then taps to draft. `draft_replies` without the author's handle can only mean the post they're on. The face button on someone's moment (`askAbout`) opens the conversation about that post, with prompt chips. `draft_replies` must name the post's author as well as its number, so a reply can't land on the wrong post.
- The brain (`lib/companion/brain.ts`): with `GROQ_API_KEY` set, a message goes to a model with a fixed persona and the tools in `lib/companion/tools.ts` (threads and their fields, memories, page search, today's page and its questions, settings and names, people, opening any page, `offer_choices`), then the last eight messages, then their newest message with what Maru knows right now (names, calendar, threads with their latest values, memories, moods, the last three pages, the daily page's questions, the screen when it matters). The persona and tools come first and stay the same, in a fixed order, so Groq caches them, and cached tokens don't count against its limits: keep anything that changes out of the system message. A keyword router (`toolsFor`) sends only the groups a message (and the one before it) points to, since each definition costs tokens; a pure question gets read-only tools.
- Honest and cheap by construction: a tool that can't do it throws `Unable`, so the model reads why; when every tool succeeds the turn ends there, since the receipts say it. One more round only when a tool failed or found something to read, a message with several things got just one after a first round that worked, a "can't" needs every tool, a reply claims an action no tool took (`tool_choice: "required"`), the model said nothing (it must offer choices), or it wrote itself a note about what to offer ("Offer to add a reminder…": `clean` cuts the note, and one round offers it as a choice while the rest of the reply stays). "Open my letters" is matched in code (`placeAsked`) with no model. Client actions come back with the reply: navigate, theme, refresh, `replied`, and `page-write`, which an open `EntryForm` appends through the `maru:page-write` event. Scripted check-in replies stay on the rules engine (`engine.ts`), which also answers news when no key is set or no model can take the turn.
- Groq calls go through `complete()` in `lib/ai/groq.ts`, which walks a list of models (free-tier limits are per model: 1,000 requests a day and 8,000 tokens a minute each) and falls back on rate limits, retired models, timeouts and tool calls Groq rejects; a conversation's first call waits once (up to six seconds) when every model is out of its per-minute tokens. The conversation uses `TOOL_MODELS` (gpt-oss first: Qwen without thinking often answers "Done." without calling the tool). Pages are read with the model on the writer's own save and at most every ten minutes while autosaving (`lib/companion/pages.ts`).

## Sign-up, pages and messages

- Onboarding asks what fills someone's days, not only their job: fifteen roles (`ROLE_KEYS` in `lib/types.ts`), from developer and teacher to shift work, parent or carer, training for something, looking after myself and retired. Each has a starting page (`lib/roles.ts`), things people in it tend to have going on and topics (`components/onboarding/script.ts`), opening questions (`lib/companion/copy.ts`) and questions in the bank. The topic chips come from the bank's tags, so a new topic needs questions behind it (`lib/questions/bank.ts`; ids are stored in saved pages, so never rename one).
- A writer's page layouts all stay: making, copying or switching never removes one. "Your pages" at the top of the gallery lists them (`myPages` in `lib/templates/mine.ts`, `GET /api/templates`), switches today's page (`POST /api/templates/[id]/use`, or `use_page` in chat) and deletes any but today's. A saved page keeps its own questions and answers, and saving today's page keeps answers to questions the layout no longer asks (`savePage`), which the writing page shows as "Earlier today".
- Messages are one conversation per pair (`Conversation`, `DirectMessage`, rules in `lib/social/messages.ts`): anyone with a handle can write to someone public, someone who follows them, or someone who put their name on a gallery page (`Template.credit`, off unless they choose it in Settings, where publishing lives). Either person can block the other. `/messages` lists conversations and `/messages/[handle]` is one (both panes on a desktop); an open conversation checks for new messages every few seconds while visible, and the shell's count every half minute. Profiles have a Message button, a credited gallery page an "Ask … about it" that starts a conversation with an opener (`?draft=`), and Maru drafts messages (`draft_message`) that go only on the writer's tap (`send_message`).

## Breakdowns

- A breakdown is how a stretch of time went, worked out in code from what the writer logged (`gather` in `lib/breakdowns/stats.ts`): threads done, moving (updated and not stuck at the end) and stuck, threads started, habit days, logged numbers, pages, moods and posts. Habit days come from `Thread.doneDays` (kept by `habitDone`, so pass it the whole thread), the run a streak ends on, and days with numbers. No model decides any of it, so the same stretch always gives the same breakdown.
- The score out of 10 (`scoreOf`) has three parts, all shown: days with something logged, open threads finished or moved (a week asks four of them, longer stretches more), and days habits were kept. A part with nothing to go on is left out; nothing logged means no score. Today only counts once something happened in it. The page says how it's worked out: never present it as Maru's judgement.
- Stretches are the writer's local days, read in code (`parsePeriod` in `lib/breakdowns/period.ts`: "last month", "since Oct 3", "October", "2026-10-01 to 2026-10-15"; weeks start on Monday) and named from the day they're viewed (`periodTitle`: "This week so far", "Last month").
- Weekly ones are made the first time the writer turns up after a week ends (`ensureWeekly`, from the day's first greeting, which carries it as a receipt, or the Breakdowns page); a week with nothing in it is kept but never listed. Asked ones come from the page's chips or from Maru (`make_breakdown`; with no stretch named it offers this week, last week, this month and a form for any other) and go after thirty days unless kept (a TTL index on `expiresAt`). Asking for a finished week that has its weekly one brings that one up to date.
- Maru's take, two or three sentences, is written once, the first time a breakdown is opened (`writeTake`, `POST /api/breakdowns/[id]/take`). It gets the facts in words without the number, or it repeats the score.
- "Give me a breakdown", "break down last month" and "how was my week" are matched in code (`breakdownAsked`) with no model. Anything else goes to the model, and the keyword router adds `make_breakdown` even to questions. A reply that reads the breakdown back is dropped: the receipt says it.

## Layout and copy

- Gutter `px-margin`; signed-in pages sit in `AppPage`. A new signed-in route also goes in `PROTECTED` in `proxy.ts`: pages read `session!`, and the layout's redirect doesn't stop them rendering. `AppShell` gives a desktop rail and, below `lg`, a top bar and a bottom tab bar. Touch targets are at least 44px. Single-column grids use `grid-cols-1` so wide children can't widen the page. No horizontal scroll at any width.
- Copy is short, specific and true, in sentence case, no exclamation marks. No invented proof (users, quotes, counts) on public pages; demo content is labelled as an example.
- Kata is for anyone's days, not only people at desks: don't write copy that assumes a job, a project, children or a partner.

## The Lab and the looks

`/looks` shows the three candidate looks (Sticker book, Night shift, Daylight) on demo data; Sticker book was chosen. Delete `app/looks` and `components/looks` once nobody needs the comparison.

`/lab` holds clickable prototypes of social features under consideration: Circles, The Sunday Post, Sealed, Promises, Kasane, Leaves & the Shelf and Pressed Flowers. The full set of 16 scored concepts lives in `components/lab/concepts.ts`.
- Prototypes run on demo data and local state only (shared cast in `components/lab/cast.ts`), with no APIs or models. Each one lives in `app/(app)/lab/<slug>/` plus `components/lab/<slug>/`, inside `LabFrame`.
- A screen opens another screen with `showLabScreen(id)` from `LabFrame`.
- `PersonSeal` (a vermilion frame with an initial) is a person's seal; `Seal` (solid, with 型) is Kata's own. Keep them distinct.
- Verdicts (Keep / Maybe / Not for us) are stored only in the viewer's browser. When an idea graduates, build it properly in the app and delete its Lab folder.
